# ADR 0006 — A birthday authorises a reference; it is not a start height

- **Status:** Accepted
- **Date:** 2026-08-23
- **Related:** ADR 0003 (the mechanism and the `height <= birthday` guard), ADR 0004 (published references), ADR 0005 (surface parity), `packages/core/src/sync/preseed.ts`, `packages/core/src/sync/wallet-sync.ts`

## Context

The birthday is repeatedly read as "the height the sync starts from". It is not,
and the difference decides whether a given wallet can sync in seconds or only in
about an hour. The misreading survives because both stories predict the same
behaviour for the case people test most — a wallet made minutes ago, where a
reference happens to exist below the birthday — and they diverge only for an
older account, where the result looks like a bug.

Recorded here because it has now been rediscovered three times: once from a
misleading comment (ADR 0003), once in a support thread about a wallet importing
from main, and once against a funded test wallet whose DUST would not sync no
matter which pre-seed reference was installed.

## What the sync can actually be told

A sub-wallet has two entry points, and only two:

```ts
CustomShieldedWallet(walletCfg, shieldedBuilder).restore(savedShielded)  // from serialized state
CustomShieldedWallet(walletCfg, shieldedBuilder)                        // from genesis
```

`WalletFacade.init(initParams)` and `facade.start(shieldedSecretKeys, dustSecretKey)`
accept no height, index or offset. There is no parameter anywhere in the SDK
surface that means "begin at block N". So the only way to begin above genesis is
to supply serialized state that was already synced to some height — and
serialized state synced to height H **is** a pre-seed reference. The reference is
not an optimisation layered on top of a start height; it is the only mechanism
there is.

## Why a start height cannot exist

Not an SDK omission — the thing being asked for is not derivable.

- **Shielded** coins are found by trial-decrypting every output with the viewing
  key. There is no address to index, so no query can answer "did this seed
  receive shielded funds before block N". Skipping to N means asserting the
  answer rather than knowing it.
- **DUST** is generated by registered NIGHT over time and its commitment tree is
  built by replaying events in order. The tree state at N is a function of every
  event below N; there is no snapshot to jump to that is not itself a reference.
- **Unshielded** is the exception, and it is why the confusion persists: its
  cursor is keyed by address, so unshielded funds are found from the start
  whatever the birthday says. A wallet with only unshielded NIGHT therefore looks
  like the birthday worked, and only DUST reveals that it did not.

Replaying those events is exactly the work a fast sync skips. A height alone
skips nothing, because nothing has been computed.

## Decision

**The birthday is an authorisation, not a starting point.** It answers "is this
reference safe for this account?" and nothing else.

```
reference at height H  +  birthday B  →  usable iff H <= B
```

Restoring a reference means asserting the account had no history below H.
That is only true when the account did not exist below H, which is what the
birthday states. With no reference at or below B there is nothing to restore, so
the sync starts at genesis — correctly, not as a fallback that failed.

Three consequences follow, and all three are intended:

1. **A birthday on its own buys nothing.** It has to be paired with a reference
   at or below it. `moth preseed status` reports `earliestSeedableBirthday` for
   this reason: it is the lowest birthday any locally held reference can serve.
   The birthday is the bound for *shielded*; per-sub-wallet bounds are a further
   refinement rather than a contradiction of this rule (issue #71).
2. **An older account cannot seed from a newer bundle, ever.** A seed first used
   at 1,696,806 gains nothing from a bundle at 2,203,416 — the bundle holds no
   record of the 506,610 blocks in between, and those must still be scanned.
   Installing more recent references does not help and is not a fix to attempt.
3. **A later birthday is a claim about history, not a speed setting.** Asserting
   one to gain speed trades correctness for it: unshielded funds are unaffected,
   but a shielded receive below the claim is silently absent from the balance.
   Nothing is destroyed — clearing the sync cache rescans — but until then the
   wallet understates what it holds.

## Options considered

**Pass the birthday to the SDK as a start height.** Rejected: no such parameter
exists, and the section above is why one cannot be added without changing what a
synced wallet means.

**Synthesize state at the birthday.** Rejected. Producing state at H requires
replaying to H, which is the cost being avoided. It is the same work as building
a reference, so it is better named that.

**Refuse an import whose birthday no reference can serve.** Rejected as too
strong. A genesis walk is correct, only slow, and refusing the import would block
a legitimate account for a performance reason. Both surfaces warn instead, naming
the reference height and the birthday, and say the first sync will start from
genesis — see `birthdayOutlook`.

**Gate each sub-wallet on its own bound, not one birthday for all three.**
Deferred, and the better option where it applies — see issue #71. DUST is
non-transferable, so generation is the only way a wallet comes to hold any, and
generation requires a registration. The first generation entry for a wallet's
dust address is therefore a hard lower bound on when it could hold dust, and
unlike a shielded birthday it is address-keyed and so *provable* rather than
asserted. Where a seed's first activity is old but its registration is recent,
the dust floor can sit above a bundled reference while the birthday sits far
below it — and DUST is 99.2% of a preprod first sync.

Measured before being believed, with `scripts/e2e/probe-dust-floor.mjs`. On the
preprod wallet that prompted this ADR the floor is 1,697,238 against a birthday
of 1,696,806 — 432 blocks apart, because it was registered the same week it was
funded. For that wallet the change buys nothing. The gain is real but not
automatic, and it does not remove the need for a reference: it changes which
references qualify, not whether one is required.

**`preseed build --height <N>`, archiving at an arbitrary older height.**
Deferred, and the only option that helps an account whose dust floor is also old
— such as the one measured above. `preseed build`
only builds at the current chain tip today, so no reference below an existing
bundle can be produced at all. Walking to N and archiving there would make older
accounts seedable at the cost of one genesis walk per target height, paid once
per network by whoever builds it. Worth doing when there is a reason to make a
specific older cohort fast; not worth doing speculatively, since each archived
height costs storage in every store that holds it.

## Consequences

- The fast path requires **both** halves. Documentation must say so wherever it
  mentions birthdays; a sentence naming only one half is what produced this
  misreading.
- Diagnosing "why is this slow" starts with two numbers, not one: the account's
  birthday and the heights of the references present. `moth preseed status`
  prints both, and the sync logs the comparison it made at verbose level.
- Test wallets intended to be fast must be **created after** the reference they
  will seed from. A long-lived funded wallet is the wrong instrument for
  measuring first-sync speed, and reusing one is how this was rediscovered.
- The `height <= birthday` guard from ADR 0003 is not a safety check bolted onto
  a feature. It is the feature's precondition.
